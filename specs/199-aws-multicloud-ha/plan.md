# Spec199 preparation plan

**Status**: Draft sequence for the next feature; execution has not started. This is not an infrastructure apply plan.

## Phase 0 — establish the actual environment

Read the current operating instructions and Spec198 closure. Discover the available AWS connector/CLI and authentication workflow without exposing credentials. Inventory all regions/services relevant to the requested topology and obtain actual billing/currency context. Research current official AWS image, instance, networking and pricing documentation only after the account constraints are known. Record unsupported/unknown capabilities explicitly.

## Phase 1 — resolve consequential scope and cost

Present the smallest concrete AWS architecture that retains three regional failure domains and existing authority guarantees. Define the exact interoperability matrix and whether any retired cloud must be recreated. Obtain the separate resource/spend delegation before provisioning. Establish full reservations, deadline, exact ownership identifiers and evidence-first cleanup behavior. Do not inherit Spec198's completed reservation.

## Phase 2 — specify and implement in a fresh feature context

Revise spec/plan/tasks/research around the accepted choices, then select a fresh199 work branch. Baseline existing driver behavior; implement the smallest AWS lifecycle adapter and tests needed for its actual IAM/network semantics. Keep application authority cloud-neutral. Validate frozen Linux dependency imports and host-appropriate member relay without provider effects. Review any changed qualified authority/client code before signed preparation.

## Phase 3 — bounded actual qualification

After the approved preflight, freeze fresh manifests/identities and activate only the exact reviewed resources. Measure regional quorum/admission timing before spending on the full matrix. Prove actual member effects and durable ACKs through every selected ingress, actual successor execution, native client recovery, and fail-closed controls. Stop at unexplained unknowns and retain their identities/evidence; never solve a failure by replaying it.

## Phase 4 — evidence, teardown and closure

Quiesce and export every authority/member store and original signed envelope. Seal immutable snapshots, excluding live-growing diagnostic logs. Remove only verified owned resources plus any specifically authorized residuals; confirm absence directly with owning-service APIs, since aggregate inventories can lag. Close ledger entries and unload finite watchdogs only after absence. Reconcile posted bills with conservative outstanding reserves, record qualification limits and obtain any required source/release approval.

## Implementation choices deliberately unselected

No AMI, instance family, region set, VPC shape, transport endpoint, IAM role, managed service, pricing rate or watchdog implementation is selected by this intake. Those choices depend on Phase0/1 evidence. Source/client publication is outside the current authorization.
