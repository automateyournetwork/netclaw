## Gaps and findings (stated plainly)
1. **Member enrollment and a member-executed operation were not done in R09A** (T021 second half). Leader election and a real model operation (guarded chat turn) ran through each Border; the R09 member executor sits outside the sandbox by design (D1) and was not rebuilt on these VMs.
2. The long-running **OpenClaw gateway daemon and workspace backend** were not run; the guarded turn uses the embedded agent (`openclaw agent --local`) with the DefenseClaw plugin. The runner's `CTL/run-script` hook used to start these pieces is a **lab-only** backdoor and must not ship in a production node.
3. The node guard configuration is the qualified R04A file with three documented deviations (`r09a_defenseclaw.py NODE_DEVIATIONS`): `data_dir` to `/sandbox/.defenseclaw`, the per-operation provider fence `base_url` removed, `forward_custom_headers: true` (else Anthropic returns 400 `anthropic-version header is required`). Mode, fail-closed, regex-only detection and the strict rule pack are unchanged. **This is a second guard topology** (no per-operation call fence or two-call counter); owner review needed.
4. OpenShell facts learned live: protocol must be `rest` (not `https`); `forward start -d` output must go to a file; provider env placeholders require an endpointless profile plus `credential_binding` in policy; supervisor egress originates from the host OUTPUT chain; the DefenseClaw CLI venv needed `go+rX` in the image (fixed in `r09a_image.py`, image `nc183-node:4`).
5. During the leader upgrade the surviving follower did not take leadership before the old leader returned (leader came back at epoch 17); the epoch jumped 15 to 17 without an observed leader on A. Not diagnosed.
6. The posture `etcd-voter` state is `unknown` by design (outside the sandbox).

## Second window (2026-11-11): the two documented gaps
The stage was rebuilt from scratch on fresh VMs (new node identities, DNS names, certificates and etcd; same tooling) and torn down again.
- **Round-trip overhead (closed)**: a request through the OpenShell forward into the sandboxed ingress (new TLS connection each time, 688-byte posture body) took a median of **19.2 ms (p95 21.7)** on node A and **17.4 ms (p95 19.8)** on node B, against **0.7 ms** for a plain host HTTP server returning the same bytes. About 17-19 ms of overhead per hop is under 0.5 percent of the signed 4500 ms admission window (`evidence/roundtrip-overhead.json`). The `no_quorum` detection times measured earlier (about 3 s) are also inside the window.
- **Member enrollment (done)**: a fresh member identity (`r09_member.py identity`, pyATS flavor, public material only) was enrolled into the two-Border sandboxed cluster with the production `Authority.campaign` + `OperationLedger.enroll_member`, both Borders stopped for the lease to expire, run as Border 0 against the etcd voters: `{"enrolled": "nc182-r09/pyats-94e835", "provisioning_epoch": 5, "lease_renewed": false, "execution_dispatches": 0}` (`evidence/enrollment-output.txt`). Both sandboxed Borders restarted and rejoined (epoch 8, one leader, one follower; `evidence/ha-enroll-window.jsonl`).
- **Member-run operation (not done in this window; closed in the third window below)**: no member executor ran. It needs the R09 member stack (frozen member source, the guard container and either a NetBox endpoint or a pyATS device, or a local model namespace), none of which exists in this environment; building it was out of proportion for this stage. The guarded model operation inside each Border sandbox (benign turn, block, fail-closed) was re-verified on the rebuilt nodes.
- **Findings from the rebuild**: (1) the mesh firewall rule must allow etcd client port **12379**, which the deploy script lacked (fixed in `scripts/ha-r09a-deploy.sh`); (2) sandbox nodes need `r09_prepare --node code=internal,public,<GCE internal DNS name>` so etcd endpoints and the cluster dial use names (OpenShell refuses IP literals); (3) mounting a state directory over `/sandbox/nc182` in the image breaks traversal, so one-shot host-side tools mount at `/mnt/nc182`; (4) a stale tar from a previous attempt silently supplied old etcd certificates: always verify `peer.crt` hashes after placing voter material.

## Third window (2026-11-11): the member-run operation (closed)
Rebuilt the stage a third time (new identities, DNS `nne1-5a89cc` / `nne2-7cc42a`, certificates, etcd; same tooling) and ran a real member through the sandboxed Borders. Owner choice: a small IPv4 subnet calculator member on the hosted Sonnet 4.6 profile (no NetBox, no device, no local model namespace).
- **Member**: new hosted `subnet` flavor in `labs/ha/r09_member.py` (identity, freeze, python-env, artifacts, materialize, validate; the qualified native summary calculator and the qualified hosted guard configuration, secrets only in `guard.env`). It ran on the owner's Mac with the production launcher (`protected-role.py run`, empty environment); `member-daemon-status.json`: `authenticated: true`, `attachments: 2` (one outbound attachment to each sandboxed Border).
- **Enrollment**: `{"enrolled": "nc182-r09/hsubnet-c3408a", "provisioning_epoch": 5, "lease_renewed": false, "execution_dispatches": 0}`; both Borders restarted and the cluster returned to one leader and one follower at epoch 8 (`evidence/member-enrollment-output.txt`, `evidence/ha-member-enroll-window.jsonl`).
- **Operation via the leader (nne1)**: `subnet_calculator 192.0.2.0/26` prepared and approved through the Border's HUD owner API: `dispatch_claimed`, `member_admitted`, then `completed` after a reconcile; outcome `succeeded`, durable ACK true, `independent_verification: true`, 2 model calls and 1 tool call (both ledgers `finished`), broadcast 192.0.2.63, 62 usable hosts (`evidence/member-op-via-leader.json`).
- **Operation entering via the follower (nne2)**: same operation; the follower forwarded it to the leader and it completed with the same result and a durable ACK (`evidence/member-op-via-follower.json`). The member's inference ledger shows ordinals 1 and 2 `finished` for both operations (`evidence/member-inference-ledger.txt`).
- **Finding (product behaviour, not a defect)**: a Border learns the member's result only through `reconcile` (it asks the member for `execution/status` then `execution/result` and sends the ACK). The VS Code and HUD owner clients request this; a bare driver that never reconciles leaves the operation in `member_admitted`. `labs/ha/r09a_run_operation.py` reconciles.
- **Qualified-code change (for owner review)**: `scripts/lib/protected_role.py` allowed a member's manifest to list only exactly 3 Borders (`ha_outbound_topology_required`); it now accepts 2 to 3 nodes because the sandboxed cluster has 2 Borders and an etcd witness (the manifest schema already allowed 1 to 3). Also `labs/ha/r09_prepare.py` reads `state_dir`, `sandbox` and `witness` with defaults so the existing member fixtures run again (91 member tests pass).
- **Teardown**: the stopped per-operation member containers (guard, relay, agent) and networks of the two operations (exactly the names in each operation's `cleanup.json`) were removed; instances, disks, addresses, three firewalls, the subnet and the network were deleted (a label and prefix listing returned nothing); the two GoDaddy A records were verified against this window's IPs and deleted; the member directory (key, guard credential), run directory, certificates, scratch venv and image context were deleted. Raw audit exports are in `~/.local/share/netclaw/r09a-evidence/export3-*`. Cost of this window: roughly 1.5 hours of VMs (about $0.30).

Result: every R09A item in the brief now has live evidence. The only open items are the owner's review of the qualified-code list and the follower not taking leadership during the leader upgrade (epoch 15 to 17, not diagnosed).
