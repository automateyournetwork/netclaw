# Proposed interface

## Registration and dispatch

Use server-start configuration to select trusted local modules. Register a stable adapter ID and a finite map of exact method, literal operation path, input schema, size limit, timeout and read or mutation classification under a reserved host prefix. Reject duplicate IDs, overlapping routes, unsupported verbs, wildcard segments and encoded path aliases at registration or dispatch. Reserve the namespace before any generic route, fallback or automatic HEAD response. The host owns request decoding, denial responses and response emission. Handlers receive validated data and a scoped owner context. Do not pass Express request/response objects, cookies, arbitrary destination URLs or filesystem binding paths. In-process modules are trusted code.

For local owner mode, mount the dispatcher after local/profile policy and before global JSON parsing or cookie rewriting. Resolve the installation-bound store early enough to reuse its existing reader. Inspect original header multiplicity and require exactly one installation-named owner cookie and one matching installation header. A legacy cookie alone cannot satisfy this route. Count request bytes while reading, cap outstanding calls and response size, impose deadlines and omit credentials, bodies and handler exceptions from diagnostics.

## Owner context and request origin

Produce a server-only handle, for example a keyed digest of an unambiguously encoded adapter ID, installation ID, runtime and verified owner token using a random per-process key. Include owner expiry, installation and runtime in the context, together with revalidation and an abort signal. Each check resolves the **same** live owner and deployment eligibility. A best-effort revocation or shutdown notification lets the adapter evict grants. Expiry, release-time revalidation and bounded downstream grant lifetimes also apply when files change externally or shutdown is abrupt. Do not use a handle as a bearer credential on a network.

For local owner mode, allow only configured loopback UI/API origins on a qualified local-only deployment. Deny local owner dispatch on a remotely exposed UI, proxy or other unqualified ingress. If the deployment cannot establish that boundary, keep the route disabled. Do not infer it from forwarded headers. A same-origin browser GET may omit Origin. Permit that case only behind the local deployment and host checks with an explicit installation header, a valid owner and no cross-site fetch metadata. Validate any supplied Origin exactly. Reject missing, duplicated or foreign Origin on mutations and require a short-lived host-validated nonce bound to adapter and owner, delivered through a protected no-store bootstrap. Limit session-status reads and nonce storage, expire them and rotate proofs on sign-in/out. A second tab can request a fresh proof after a rejected stale one.

## Dedicated HTTPS reviewer entry point

Serve the embedded HUD review view from an explicitly configured, distinct HTTPS hostname and isolated listener. Its entire route table consists of its static review shell, bounded session bootstrap, sign-in/out and the selected adapter operations. Reject all other paths and methods including local owner issuance, legacy APIs, SSH, chat, model controls and WebSocket upgrades. The regular local UI and its proxy cannot forward traffic to this listener as trusted owner traffic. Serve dedicated reviewed assets with restrictive CSP and frame-ancestors policy. Do not load the ordinary dashboard startup code, service worker or privileged origin storage. The view registry must explicitly support the reviewer profile when selected. Reuse view rendering and the narrow operation schema while keeping the local and network session checks separate.

Authenticate the HTTPS server to browsers with a trusted certificate. Protect the browser-to-listener connection end to end, or explicitly authenticate a TLS-terminating ingress to a private listener and close every bypass. Do not infer identity, scheme or authority from client-supplied proxy headers. The listener pins the installation and service origin in server configuration. It authenticates to the service with a per-installation credential over validated TLS. Convergence uses a per-installation client certificate; its API checks the grant and installation independently. The user signs in through the review shell to the application. TLS alone does not identify a person.

A bounded, unauthenticated bootstrap returns a CSRF proof and an anonymous host-only pre-session cookie. Require the exact configured HTTPS Origin, JSON and the proof on sign-in. Rotate the session ID and CSRF proof at sign-in, and invalidate any older login attempt at sign-out. Bind the application's user grant to this review session, installation, adapter, process and expiry. Use a Secure, HttpOnly, SameSite=Strict, host-only cookie with a __Host- prefix and Path=/. Keep per-user grants server-side. Authorize the allowed app, role, site and case on every operation; reject session fixation, unexpected inputs and client-supplied actor fields. Include expiry, throttling and current-grant revalidation at private response delivery. No local NetClaw owner cookie is issued or accepted in this mode. Logout and role changes take effect independently for each reviewer.

## Async work and failure

Check the owner before dispatch and again before returning the bounded private result. The adapter independently rechecks its current user grant. Send no private result after revocation, installation switching or client cancellation. Abort on disconnect or deadline. A timed-out handler may already have committed a write, so each mutating service owns transaction-time authorization, audit and retry/reconciliation. Never retry a mutation in the host. Rollback disables registration, drops adapter associations and revokes outstanding downstream grants according to the service contract.
