# Teaching NetClaw to Open Change Requests — a HaloPSA / HaloITSM MCP

*Draft milestone post (Constitution Principle XVII). Authored collaboratively by John and Claude. WordPress MCP is not configured in this environment — publish manually.*

## What we built

Feature **069** adds a **Halo MCP server** to NetClaw — one server for **HaloPSA and HaloITSM** (they share a single REST API, "Halo API"). It does two jobs an MSP actually asks of its PSA/ITSM:

1. **Open change requests** — a single, gated, confirm-before-submit write.
2. **Review assets and their related tickets** for operational context.

18 tools — **17 read-only + 1 gated write** — across ticket types, fields, tickets, assets, clients/sites/users/contracts, and knowledge base. Three skills (`halo-change-request`, `halo-asset-context`, `halo-ticket-context`), a 130-test suite, and a clean end-to-end smoke against a live Halo tenant.

## Why it matters — and why it's hard

Halo is **heavily customized per organization**. "Change request" isn't a fixed thing: it's a *ticket type* whose id and whose custom-field set differ at every customer. You can't hardcode it. So the change-request skill has to be a little bit clever:

1. **Discover** the org's change ticket type (`halo_list_ticket_types`), and **confirm it with the operator** — Halo's vocabulary calls ticket types "Request Types," and there may be several change-shaped ones.
2. **Remember** the confirmed type in Memory MCP (`memory_record_fact`), so it only asks once.
3. **Learn the fields** — read the ticket type's authoritative field schema (`halo_get_ticket_type`) *and* a real sample change (`halo_get_ticket`) for a concrete example.
4. **Assemble, preview, and only then create.**

## Three decisions that shaped it

**OAuth2 client-credentials.** Unlike the read-only Auvik server (HTTP Basic), Halo uses OAuth2. The client fetches a bearer token from `<base>/auth/token`, caches it until expiry, and transparently refreshes on a 401. Tokens, not passwords, on every `/api/*` call.

**Confirm-before-submit, structurally.** Creating a change is the one write, and Halo *is* the system of record — so the gate is built into the tool, not just the prose. `halo_create_change_request(submit=false)` (the default) resolves ids, assembles the exact `POST /api/Tickets` body, and returns it as a **preview** — no HTTP write. Only a follow-up call with `submit=true`, after the operator approves the previewed change, actually creates it. Halo's own CAB/approval workflow takes it from there.

**Halo speaks in ids; operators speak in names.** Tickets are "Faults," assets are "Devices," and everything is addressed by opaque number. Every tool that can resolves a name / inventory number to the right id first, and the POST body carries `tickettype_id` + a `customfields[{id,value}]` array (the same numeric id is a field's definition, its value on a ticket, and its placement on a ticket type).

## How it was built

Spec-Driven Development (Constitution XVI) executed by a fleet of focused subagents: the OAuth client, pagination, resolver, and models were laid down as a shared foundation, then **two subagents built the six tool modules in parallel**, and three more wrote the test suite, the skills, and the SDD spec docs concurrently while the coherence wiring (catalog, installer, HUD, SOUL/README/TOOLS, the 12 Principle XI touchpoints) went in alongside. Test-driven throughout — **130 mock-based tests**, green.

Then we pointed it at a real Halo tenant, and the exercise earned its keep three times over:

- **A real backoff bug, caught by TDD.** The 429 `Retry-After` handler was silently dropping the server's requested delay: `dict(resp.headers)` lowercases the header name to `retry-after`, but the parser looked up the capitalized `Retry-After`, so it always fell back to a hard-coded 1-second wait. A unit test pinned it; the fix passes the case-insensitive headers object and makes the parser case-insensitive too. (The same latent bug turned out to live in the Auvik client we based this on — flagged for a follow-up.)
- **Typed tool params bite the harness, not the server.** The first live run failed 12 of 18 tools with schema-validation errors — because the smoke harness captured Halo ids as integers and handed them to tools whose params are typed `str`. FastMCP's schema validation correctly rejected them. A one-line `str()` in the harness, and all 18 went green. A good reminder that the MCP boundary is typed, and that "it worked in the mock" and "it validates over the wire" are two different tests.
- **The safety gate holds against the real thing.** On a live tenant with 105 clients and 6,360 field definitions, `halo_create_change_request(submit=false)` assembled a correct change body against the org's real change ticket type (auto-discovered) and **created nothing** — `{"preview": true, ...}`, zero writes, confirmed both by the mock suite and against production.

Final live smoke: **18/18 tools OK.**

## Lessons learned

- **Model the customization, don't fight it.** The whole change-request flow exists because Halo's change ticket type is per-org. Discover → confirm → remember beats any hardcoded assumption, and Memory MCP makes "ask once" real.
- **Make the safety gate structural.** A "please confirm first" comment in a skill is a suggestion; a tool that literally cannot write unless `submit=true` is a guarantee. Preview-by-default meant the very first live call against production was provably harmless.
- **Green mocks are necessary, not sufficient — and the wire is typed.** The Retry-After bug and the int-vs-string mismatch both passed (or never ran through) the mocked path. Only the real token flow and the real MCP schema boundary surfaced them.
- **Copy a pattern, inherit its bugs.** Basing the client on Auvik's got us a proven shape fast — and carried a latent bug forward. Worth grepping the source you cloned when you find a defect.
