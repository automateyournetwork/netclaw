# Teaching NetClaw to Speak Auvik — A Read-Only MSP Monitoring MCP

*Draft milestone post (Constitution Principle XVII). Authored collaboratively by John and Claude. WordPress MCP is not configured in this environment — publish manually.*

## What we built

Feature **036** adds an **Auvik API MCP server** to NetClaw: a read-only, FastMCP/stdio server that turns Auvik's network-monitoring API into 20 tools the agent can call, organized around the four things MSP operators actually ask about — **inventory, network alerts, lifecycle, and performance** — plus a billing/usage view of inventory. It ships with four skills (`auvik-inventory`, `auvik-network-alerts`, `auvik-lifecycle`, `auvik-performance`), a 381-test suite, and a clean end-to-end smoke against a live Auvik tenant — a real 178-client MSP account.

## Why it matters

Auvik is where a lot of MSPs keep ground truth about *what's on the network and how it's behaving*. Wiring it into NetClaw means an operator can ask, in plain language — "is core-sw-01 healthy?", "what critical alerts fired overnight for the Dallas client?", "which devices are past end-of-support?" — and get an answer without touching the Auvik UI or memorizing an API.

## Two decisions that shaped the design

**Operators speak in names, not IDs.** Auvik addresses everything by opaque IDs, but nobody says "show me device 242216279026467843." So identifier resolution is a first-class, cross-cutting capability: every tool accepts a name, hostname, or IP, resolves it to the right Auvik ID, and — when a name is ambiguous — returns the candidate matches and asks rather than guessing. A wrinkle we found in the spec: Auvik's device/network/interface list endpoints have *no* server-side name filter, so resolution fetches and matches client-side (which is exactly why the next decision mattered).

**Real result sets span many pages.** Auvik paginates with JSON:API cursors, and its `meta.totalPages` is deprecated. The client auto-follows `links.next` and aggregates every page up to a safety cap, flagging truncation with a continuation cursor — so a "list the devices" answer is the *whole* list, not a silently truncated first page.

**Read-only by construction.** The one mutating endpoint Auvik exposes (`alert/dismiss`) was deliberately left out. There are zero write tools, no `post`/`put`/`delete` anywhere in the client — verified by test and by source grep. Observability shouldn't be able to change the thing it observes.

## How it was built

Spec-Driven Development end to end (Constitution XVI): a ratified spec, then a plan set (research, data-model, tool contracts, quickstart, tasks), then test-driven implementation executed by a fleet of focused subagents with a two-stage review after each unit. That review caught two real defects before they spread — a subagent that hallucinated Auvik's `deviceType` enum, and a planning assumption that a name filter existed where it didn't. Every turn was recorded in an immutable GAIT session log (Constitution IV).

Then we pointed the finished server at a real Auvik tenant — a **178-client MSP account** — and drove all 20 tools *through the real MCP server over stdio*, the way OpenClaw actually calls it. The live API immediately earned its keep, catching a series of things the mocked unit tests had waved straight through:

- **Wrong cluster, silently.** The tenant lives on Auvik's `us2` cluster, not the `us1` default; every data call `308`-redirected to us2 and the client — which doesn't follow redirects — failed. One env var (`AUVIK_BASE_URL`) fixed it, but nothing had *told* us so.
- **Empty 200s and name-vs-ID params.** The credential-verify endpoint returns an empty `200`; the client called `resp.json()` unconditionally and threw. And `tenants` wants Auvik's opaque IDs, not names — passing a name returned a clean `400`. Two success-shaped responses that weren't; we added empty-body handling and tenant name→ID resolution across all 17 tenant-aware tools.
- **MSP endpoints demand scope.** With 178 tenants, the data endpoints reject *unscoped* queries with a `403` — they require a `tenants=` filter. `verify` and `tenants` answer unscoped; nothing else does.
- **An ordering bug only a *full* re-run surfaced.** With the unit suite green, a device-by-name query *scoped to a tenant by name* still failed with a misleading "not found" — the tool resolved the device before the tenant, feeding a raw tenant name into the inner lookup. Only re-running the entire end-to-end smoke, not the units, caught it.
- **"Optional" that isn't, and a real crash.** The statistics endpoints reject a request with no `thruTime` (`400`) despite the tool marking it optional, and validate `stat_id` *per component type* (a CPU takes `capacity`, not `utilization`). And `auvik_get_usage` crashed outright — `'list' object has no attribute 'get'`. On an MSP account, `/v1/billing/usage/client` returns `data` as a **list**, one row per tenant, but the single-resource shaping helper assumed a dict. The unit suite only ever mocked a single-object payload, so it stayed green. The fix teaches the helper to shape a collection into `items[]`, pinned by a test that reproduces the list shape.

Every fix landed with the suite green — **381 tests** — and the harness finishing **20/20** against the live tenant.

## Lessons learned

- **Pin your enums to the source, and test the count.** "It's a non-empty set" let a hallucinated enum through; "it has exactly 48 values including `multimedia`" did not.
- **Verify the API's filters before you design resolution around them.** The missing `filter[deviceName]` would have been a runtime surprise; catching it in review made it a five-minute spec edit.
- **Make the model state its assumptions.** The strongest review signal was subagents *documenting* the judgment calls they made (which field to match a network name on, how to handle an ambiguous entity) — that's where a human's eye lands fastest.
- **Green unit tests are necessary, not sufficient — smoke the real thing.** Nearly every bug above passed the mocked suite. Mocks model the API you *think* you're talking to; an empty 200, a 400 on a name, a 403 until scoped, and a list-shaped billing payload only showed up against the real one.
- **Re-run the *whole* smoke after every change, not the unit tests.** The ordering bug hid behind a passing suite and only fell out of a full end-to-end re-run. "I changed one thing, the units are green" is exactly when the integration path breaks.
- **The account *type* changes the response shape.** A single-tenant smoke is not an MSP smoke. A list-shaped usage payload, endpoints that `403` until scoped, and a whole different cluster only appeared against a real 178-client account. Test against the *kind* of account you'll actually run in — not just a convenient one.
