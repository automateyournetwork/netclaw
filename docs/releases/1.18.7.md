# NetClaw 1.18.7

Spec: [177-defenseclaw-sidecar-identity](../../specs/177-defenseclaw-sidecar-identity/spec.md)

## Changes

- **The DefenseClaw CLI can reach the sidecar NetClaw runs.** `defenseclaw-sidecar.service`
  ran `defenseclaw-gateway` in the foreground. DefenseClaw writes its PID record only when
  started with `defenseclaw-gateway start`, so its CLI treated the running gateway as
  someone else's. `defenseclaw skill enable` and `disable` failed with "the gateway is
  not running", CLI scans were not recorded in the audit log, and a quarantined skill
  could not be re-enabled without stopping the unit.

  The unit now starts the gateway with `defenseclaw-gateway start` and stops it with
  `defenseclaw-gateway stop`. A small helper gives systemd the gateway's PID, copied
  from DefenseClaw's record, so `Restart=always` still restarts it after a crash.
  Starting the unit also takes over a gateway that was started by hand.

## Upgrade and compatibility

Existing Risk hosts keep the old unit until it is regenerated and restarted:

```bash
python3 scripts/in2n-services.py generate
systemctl --user daemon-reload
systemctl --user restart defenseclaw-sidecar.service
defenseclaw-gateway status    # should show the unit's MainPID
```

No DefenseClaw version change; tested with the pinned 1.0.4. NetClaw never writes
DefenseClaw's own PID record.

## Validation and known limitations

See [verification](../../specs/177-defenseclaw-sidecar-identity/verification.md).

- Live on the Ubuntu 24.04 qualification Risk (production mode): the CLI reached the
  supervised gateway, a SIGKILL was restarted by systemd, stop/start was clean, and
  posture stayed `production — enforced`.
- Not tested: DefenseClaw 1.0.8, macOS (launchd), and the system-wide enterprise
  gateway, which NetClaw does not generate.
