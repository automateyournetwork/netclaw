# NetClaw 1.17.1

Spec: [167-production-mode-qualification](../../specs/167-production-mode-qualification/spec.md)

## Changes

Live production-mode qualification (Risk `N2N_RISK_MODE=production` with the
DefenseClaw model guard, systemd member confinement and GAIT audit) found five gaps,
all fixed here:

- **Model-guard recognition.** DefenseClaw 1.x guards OpenClaw through a plugin that
  sends model calls to its loopback proxy (`:4000`); it does not create a
  `defenseclaw/<model>` provider. NetClaw now accepts that plugin route (enabled,
  allowed, not denied, loaded from an existing `defenseclaw` extension directory) in
  addition to the provider route. Proxy reachability and `security.mode` are still
  required, and the proxy blocks unknown provider domains fail-closed.
- **Guarded members.** `in2n-member-home.py` copies only the DefenseClaw plugin entries
  into Convergence member homes and mirrors only the Border's `security.mode` into OpenClaw
  member homes (the Hermes builder is unchanged; Hermes is not qualified), so a production member's own model calls pass through the guard.
- **On-demand routing.** `/n2n/members` and `/n2n/members/health` report
  `starts_on_route` for a down on-demand member; the observation skill tells the Border
  to route to it.
- **Gateway token SecretRefs.** `gateway_ws` resolves `source: env` SecretRefs and
  refuses other sources with a clear message.
- **Pinned DefenseClaw installation.** The enable script, installer and secure-start
  script install a pinned release whose installer is verified against the release's
  `checksums.txt`; OpenShell is opt-in and checksum-gated.

## Upgrade and compatibility

Testing-mode Risks and standalone NetClaw are unaffected. To run production mode with
DefenseClaw 1.0.4 on OpenClaw 2026.10.9:

1. `./scripts/defenseclaw-enable.sh` (pinned, verified; observe mode by default).
2. Register model providers DefenseClaw does not know, for example
   `defenseclaw setup provider add --name ollama-cloud --domain ollama.com --env-key
   OLLAMA_API_KEY --profile-id ollama-cloud:default --base-provider-type ollama`.
3. `python3 scripts/in2n-services.py generate && ... enable` (durable sidecar), then
   `openclaw gateway restart` to load the plugin.
4. Set `N2N_RISK_MODE=production`, reinstall the cold-start template if used, and
   rebuild member homes so they carry the plugin and security mode.

DefenseClaw 1.0.x `init` fails when OpenClaw's `gateway.auth.token` is a SecretRef
object (`gateway defaults: str expected, not dict`); the enable script stops and
explains the options rather than rewriting the token. This is a DefenseClaw issue.

## Validation and known limitations

On the dedicated Ubuntu 24.04 VM (OpenClaw 2026.10.9, DefenseClaw 1.0.4,
ollama-cloud/minimax-m3) the Risk reached `production - enforced`. Production runs
passed for standalone, federated (twice consecutively, with confined system cold
start of the on-demand member) and denied-scope scenarios; a member-only routed task
showed the member's model I/O intercepted, inspected and recorded by DefenseClaw.
Stopping the guard sidecar or removing the cold-start template degraded the posture
and refused delegation without starting a member. See the
[ledger](../../specs/167-production-mode-qualification/verification.md). Action
(blocking) guardrail mode, other providers and models, Hermes and macOS/WSL were not
qualified; synthetic fixtures do not establish general model accuracy.
