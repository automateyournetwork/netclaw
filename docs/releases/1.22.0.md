# NetClaw 1.22.0

Spec: [185-member-spec-providers](../../specs/185-member-spec-providers/spec.md)

## Changes

- **A member spec can use any provider the Border configures.** `"model":
  "ollama-cloud/minimax-m3"` runs the member on the Border's `ollama-cloud` provider. The
  member gets a copy of that one provider entry, with only its model, and only the variables
  the entry references (`OLLAMA_API_KEY`), never `ANTHROPIC_API_KEY`. Providers with a literal
  key, a local service (`localService`) or no such model are refused with the reason.
- **Subscription logins for members.** `"auth": "subscription"` with `anthropic/<id>` or
  `openai/<id>` runs the member on a Claude or ChatGPT account instead of an API key. The member
  holds no key; `in2n-member-home.py` prints the exact `openclaw models auth login` command for
  the member's own home, and OpenClaw keeps that login in the member's home only.
- **Staged members run on the federation runtime.** `run.sh` now execs the interpreter the mesh
  daemon uses (`python-runtimes/records/n2n`) instead of the system `python3`, which could lack
  `websockets` or a current `cryptography` and made cold-started members fail every task.

## Upgrade and compatibility

No migration. Specs with `model: null` or an Anthropic model behave as in 1.21.0. Members staged
before 1.22.0 keep their `run.sh`; re-stage a member (`in2n-migrate.py --spec ...`) to switch it
to the federation runtime.

## Validation and known limitations

See [verification](../../specs/185-member-spec-providers/verification.md): unit and fixture
tests, `openclaw config validate` on provider and subscription member homes, and a live run of
Convergence's alert investigator on `ollama-cloud/minimax-m3` on a test Border (alert case
delegated by the Border, investigated and recorded by the member). Not live-tested: subscription
logins (validated as configuration only). In production posture, models on loopback or private
providers stay refused by the DefenseClaw plugin route.
