# NetClaw 1.21.0

Specs: [183-member-mcp-mappings](../../specs/183-member-mcp-mappings/spec.md),
[184-member-spec](../../specs/184-member-spec/spec.md)

## Changes

- **Members get the MCP servers their skills call (spec 183).** Member provisioning keeps
  only the servers in `MCP_SERVERS`, and several profiles were wrong. A pyATS or CML member
  had its skills but no tools, and a GitHub member was given GitLab's server. 35 of 42
  profiles now map to the servers their skills call. The evidence is in the spec's research.
- **A member gets the variables its servers need, and only those (spec 183).**
  - **What's included:** the env slice carries every `${VAR}` its kept servers reference,
    plus the settings a component-launched server reads, from the catalog. That includes
    pyATS's device logins.
  - **What's never included:** ServiceNow and comms secrets, which reach no member by
    default. Their change gates refuse changes without them.
  - **Own `.env`:** component-launched servers read the member's own `.env`, never the
    Border's.
  - **Fails closed:** provisioning refuses to continue when that file is missing, or when
    it is the Border's `.env` or home.
- **Member specs (spec 184).** `in2n-member-home.py --spec member.json`, `netclaw risk add
  spec FILE` and `in2n-migrate.py --spec` provision a narrowly scoped member from a JSON
  file listing its MCP servers, skills and tool allowlist, with no change to NetClaw. A spec
  member:
  - has its own workspace (its skills plus the base skills), memory store and GAIT stores;
  - has a config built from an allowlist of keys, so no Border gateway token, hooks, cron,
    env vars or other provider keys;
  - has Skill Workshop off;
  - gets OpenClaw's tool allowlist and per-agent skill filter.

  Dangerous built-in tools are refused unless `--allow-dangerous-tools` is given, which is
  recorded in the member home. That covers everything except `read` and `session_status`.
  Border-only servers are refused: protocol, n2n, the HUD's private server, netconverter,
  comms and convergence-read.

## Upgrade and compatibility

Existing members change only when they are provisioned or migrated again. Re-provisioned
pyATS, CML, NetBox and similar members gain their MCP servers and variables. A
component-launched member server now needs the member's own `.env`:
- `in2n-migrate.py` prints the exact `in2n-member-home.py ... --member-env` command;
- without it, provisioning stops with an error naming the file.

Profile members still copy the Border's config apart from comms, tools and skills, as
before. Moving them onto the spec-member config is a follow-up (spec 184, Known behaviour).

## Validation and known limitations

See verification for [spec 183](../../specs/183-member-mcp-mappings/verification.md) and
[spec 184](../../specs/184-member-spec/verification.md).

- 188 tests in the two new test files pass, including runs against the installed OpenClaw
  2026.10.9's own tool-policy, sandbox and skill-filter code. The full `tests/n2n` suite
  shows no new failures against `main`.
- Not tested live: enrolling and routing a spec member, and OpenClaw refusing a disallowed
  MCP call at run time.
