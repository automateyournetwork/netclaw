Executive summary

This capture records a complete eN2N skill-delegation lifecycle between two federated NetClaw agents. John's agent opened chat sessions, attempted to delegate the pyats-health-check skill twice and was denied both times (JSON-RPC error −32001 in ~20 ms), the authorization layer failing closed exactly as designed. After the operator granted the skill at 14:09:05 — a local API action, deliberately invisible on the wire — identical re-submissions were accepted in 6 ms. One task completed in 10 m 25 s and returned a 3,114-byte fleet health report; the other stalled in “working” and refused a cancel — the one genuine anomaly. Transport was flawless: zero retransmissions, zero duplicate ACKs, heartbeats never missed.

Topology — what the two TCP streams actually are

Both streams are the same peering seen from different sides. Stream 0 is Nick's daemon dialing John's published ngrok TCP endpoint — a genuine RFC 4271 BGP session used for mesh liveness (KEEPALIVEs only in this window; no UPDATEs). Stream 1 is John dialing Nick's ngrok endpoint; the local ngrok agent terminates the tunnel and delivers it from loopback, which is why the NCFED channel appears as 127.0.0.1 ⇄ 127.0.0.1. Peer Byrn (as65099) has no direct endpoint and generated no traffic in the window.

Wire formats observed

NCFED is length-prefixed JSON-RPC 2.0 over TCP: every message is a 5-byte !IB header followed by a UTF-8 JSON body. A zero-length frame is a heartbeat. Payloads over 64 kB are chunked with the continuation flag (none needed in this session — largest frame was 3,114 B). The 13-byte handshake exchanges AS number and router-id before any frames flow; this session's handshakes pre-date the capture (see ncfed-session.pcap from 2026-07-13 for a captured handshake, n2n/hello, and the 46 kB inventory exchange).

Response latency by method — three timing regimes

The spread is diagnostic: sub-millisecond methods are pure SQLite reads/writes in the daemon; tens of milliseconds involve authz checks or endpoint upserts; ~18 seconds is a full LLM agent turn — chat/message blocks synchronously on the reply, which is exactly why tasks/submit is async (submit → poll → result) for long-running skills.

Findings

1 · Authorization enforcement verified on the wire — fail-closed, then open after grant

Two n2n/tasks/submit requests (14:05:55 frame 116, 14:07:10) were rejected with −32001 “skill 'pyats-health-check' not allowlisted for as65001-4.4.4.4” in ~20 ms while ungranted. Identical submissions at 14:10:18 (frame 295) and 14:14:18 — after grant id 3 landed at 14:09:05 — were accepted in 6 ms. The deny → grant → allow transition is fully visible in the trace, with no bypass path and no capability enumeration leaked in the error.

2 · Task 83d1176e stalled for 19 minutes and refused cancellation

The first accepted task (14:10:18, testbed-wide health check) was polled 7 times over 19 minutes and never left state=working, while its near-duplicate submitted 4 minutes later completed in 10 m 25 s. John's n2n/tasks/cancel at 14:29:30 returned cancelled=false in 0.5 ms — the daemon answered from local state without attempting runner termination. Two issues: (a) why the first runner never finished — likely both tasks contending for the same testbed; (b) cancel should terminate a working task or say why it can't. Check delegated_task for 83d1176e… and the runner logs.

3 · endpoint_update re-announce loop is 64% of all NCFED JSON-RPC traffic

114 n2n/endpoint_update requests (57 per side, one every ~28 s) plus 114 responses — ~26 kB of the channel's 94 kB — re-announced tunnel endpoints that never changed (frame 7's 8.tcp.ngrok.io:XXXXX is byte-identical all session). Re-announce should be event-driven (on tunnel change) with a slow refresh, not a sub-30-second loop; at fleet scale this dominates channel cost.

4 · The federation channel is cleartext — chat and task results readable on the wire

Every chat message, task input, and the complete 3,114-byte health report (device names, IGP/BGP topology detail) were recovered from this capture by parsing 5-byte headers. The BGP mesh session to 3.19.130.43:20203 is cleartext on the actual internet path; the NCFED channel's privacy rests entirely on ngrok's tunnel transport. Feature 056 already ships per-peer pinned keys under ~/.openclaw/n2n/keys/ — wiring TLS onto the eN2N channel would close this.

5 · Protocol correctness & transport health: excellent

137 request/response pairs, every ID matched, no orphans or duplicates. Heartbeats metronomic at 30.0 s (zero misses in 27 min); BGP keepalives steady. Zero TCP retransmissions, duplicate ACKs, zero-window or out-of-order events across 1,059 packets. Async task design confirmed on the wire: submits return in ms while the 18 s agent turns ride chat/message only.

Reproducing this analysis

sudo tcpdump -i any -nn -s 0 'tcp port 20203' -w n2n-session.pcap  # capture both mesh + federation channels
tshark -r n2n-session.pcap -q -z conv,tcp  # find the streams
tshark -r n2n-session.pcap -Y 'tcp.len>0' -T fields -e frame.time_epoch -e tcp.stream -e tcp.payload  # extract payloads
# then parse: 13 B handshake (magic "NCFED" + !I AS + router-id), else 5 B !IB header + JSON-RPC body; len=0 ⇒ heartbeat
